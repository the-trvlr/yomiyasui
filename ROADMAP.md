## 2. Выводы

**Продукт.** Идея ясная и нишевая: «спокойное чтение» для русскоязычных, изучающих японский, без аккаунтов и бэкенда. Это осознанная позиция, и её стоит удерживать: конкуренты (Yomitan + Anki, jpdb, Migaku, ttu Reader) выигрывают по функциям, но проигрывают по простоте входа. Дифференциатор 読みやすい — не словарь, а **режим чтения**: автопрокрутка, фуригана, типографика. Именно его надо доводить до совершенства.

**Технически 1.0 — это качественный прототип, который упёрся в потолок своей архитектуры.** Один файл на 2 074 строки, ноль модулей, ноль тестов, пять независимых мест с версией JMdict — каждая следующая фича будет стоить дороже предыдущей.

**Главный риск — не отсутствие функций, а то, что приложение может не запуститься на телефоне.** 33,6 МБ на первую загрузку, повторный разбор JSON и полная переиндексация словаря при каждом открытии страницы, ~200 тыс. объектов в памяти, полный рендер книги в DOM. На среднем Android это либо 20–40 секунд до первой фуриганы, либо вкладка, убитая по памяти. Всё остальное вторично.

**Сильные стороны** (не потерять при рефакторинге):
- Продуманный мобильный сценарий: раскрывающийся словарь-шторка, плавающий транспорт, `16px` в поиске против iOS-зума, `dvh`/`safe-area`.
- Честная индикация первого запуска с пошаговым прогрессом и частичным отказом функций (`bootSplash`, `failFirstSetup`) — этого нет у большинства pet-проектов.
- Аккуратная работа с недоверенным вводом: `escapeHTML` применён последовательно, XSS-векторов в найденном коде не обнаружено.
- Приватность по умолчанию: нет сети, кроме собственных ассетов и ссылки на Jisho.
- Хорошая гигиена поставки: пины версий, проверка целостности ассетов после скачивания, отдельный `check-html.mjs`.

## 3. Проблемы по приоритетам

### P0 — блокируют рост

**P0-1. Пересборка словаря при каждом запуске.**
`loadFullDictionary()` → `fetchArchive()` → `JSZip.loadAsync` → `JSON.parse` → `ingestDictionary()` → `updateDictionaryIndex()` (`site/index.html:1516–1580`). Каждый запуск: распаковка 15,4 МБ, парсинг ~50 МБ JSON, два прохода по ~200 тыс. записей, построение `formIndex` и `prefixIndex` с массивами ссылок на объекты. Пиковое потребление оценочно 200–400 МБ. Это признано в README как ограничение — но это не ограничение, а архитектурная ошибка: индекс нужно собирать на этапе сборки, а не в браузере.

**P0-2. Полный рендер книги в DOM.**
`renderAnalyzedText()` (`:1222–1247`) создаёт `<span class="word">` на каждый токен, каждый — через `innerHTML` (`:1237`). Для книги на 300 страниц это ~100 тыс. span + ~60 тыс. ruby/rt и 100 тыс. вызовов парсера HTML. Затем это пересобирается целиком при смене режима фуриганы и **при каждом переключении «известное слово»** (`:2011`). Виртуализации нет.

**P0-3. Токенизация всей книги последовательно.**
`applyText()` (`:1287–1295`) отправляет в воркер по одному абзацу и ждёт ответа: 2 000 абзацев = 2 000 round-trip. Результат показывается только после обработки **всего** текста, хотя рендер уже готов. Нет приоритета видимой области, нет отмены уже отправленных задач (`renderVersion` отбрасывает результат, но работа продолжается).

**P0-4. Линейный поиск по русским переводам.**
`searchDictionary()` (`:1777–1796`) при кириллическом запросе перебирает все записи и все глоссы, применяя `normalizeSearch` (NFKC + `toLocaleLowerCase`) и набор регулярок **на каждое нажатие клавиши**. Это ~1,5 млн строк на запрос, то есть сотни миллисекунд–секунды на мобильном. Кэша нормализованных глосс нет.

**P0-5. Позиция чтения хранится как доля прокрутки в пикселях.**
`updateSettings()` (`:848–858`) и `resize` (`:2054`) меняют высоту контента, но `offset` не пересчитывают из «якоря» — только обрезают по максимуму. Смена размера шрифта, ширины строки или поворот экрана **сдвигают читателя в другое место книги**. То же с сохранением: `progressRatio` — доля, а не `{абзац, символ}`.

**P0-6. Архитектура и процесс.**
Один IIFE без модулей, экспортов и тестов. Чистые функции (`plainDocument`, `extractHtmlText`, `translationMatchScore`, `resolveZipPath`, `dictionaryKey`, `furiganaHTML`) невозможно протестировать — они заперты в HTML. Версия JMdict продублирована в 4 местах (`:600`, `:541–542`, `ci-cd.yml`, `prepare-site-assets.sh`) и уже рассинхронизируется вручную.

## 4. Целевая архитектура

```
site/
  index.html          # только разметка + <link>/<script type=module>
  styles/             # разбито по слоям: base, shell, reader, dict, mobile
  src/
    main.js           # точка входа, композиция
    config.js         # сгенерирован из deps.json (версии, хэши)
    reader/
      engine.js       # прокрутка, якорь позиции, скорость (знаки/мин)
      renderer.js     # виртуализация абзацев, инкрементальный патч токенов
      furigana.js     # чистая функция: поверхность → HTML/узлы
    dict/
      store.js        # загрузка скомпилированных шардов
      search.js       # префиксный + глоссовый индекс
      ui.js
    library/
      db.js           # схема, миграции, квоты, экспорт/импорт
      epub.js         # OPF/nav/NCX, картинки, метаданные
    workers/
      tokenizer.js
      search.js       # опционально: поиск в воркере
  data/               # артефакты сборки, версионированные имена
    jmdict-<ver>/shards/*.bin
    jmdict-<ver>/forms.idx
    jmdict-<ver>/gloss.idx
```

**Сборка словаря на CI (ключевое решение).**
`scripts/build-dictionary.mjs` скачивает архивы JMdict и публикует готовые артефакты:

1. `terms.bin` — компактные записи (interned-строки, `Int32Array` смещений), без JSON-парсинга в рантайме.
2. `forms.idx` — отсортированный массив нормализованных форм → диапазоны id (бинарный поиск, без `Map` на 500 тыс. ключей).
3. `gloss.idx` — инвертированный индекс по нормализованным русским и английским глоссам (токен → id записей) для быстрого поиска по переводу.
4. Шардирование по хэшу формы — грузим только нужные шарды через `fetch` + `Range`.

Это убирает JSZip и `JSON.parse` из критического пути, снимает 15,4 МБ первой загрузки и делает поиск по переводу O(1) по индексу.

**Позиция чтения.** Хранить `{paragraphIndex, charOffset, ratio}`; при любом изменении раскладки восстанавливать `offset` из якоря, а не масштабировать пиксели.

**Первый запуск.** «Лёгкий режим» по умолчанию: `Intl.Segmenter('ja')` + чтения из `forms.idx` (без 17,8 МБ Kuromoji). Полный анализатор — опциональная загрузка, если нужна точная морфология. Ожидаемый бюджет первого экрана: 1,5–3 МБ вместо 33,6 МБ.

## 6. План по фазам

Оценки — «идеальные дни» одного разработчика (part-time).

### Фаза 0. Гигиена и фиксация поведения — 1–2 дня

- `LICENSE` (MIT) + `NOTICE` с атрибуцией JMdict/EDRDG, Kuromoji, JSZip.
- `package.json`, `npm scripts` (`dev`, `build`, `test`, `lint`, `check`), ESLint + Prettier, `.editorconfig`.
- Вынести `<style>` и `<script>` в отдельные файлы (`site/app.css`, `site/app.js`), обновить `check-html.mjs`.
- Единый источник версии JMdict: `deps.json` → генерируемый `config.js`; убрать хардкод из HTML и workflow.
- Мелкие багфиксы: `rt`/`rp` в EPUB, `dictFallback` после успешного импорта, `lang="ja"` на области чтения.

**Готово, когда:** поведение не изменилось, CI зелёный, файлов с версией — один.

### Фаза 1. Измеримость и тесты — 3–5 дней

- Разбить IIFE на ES-модули: чистые функции отдельно от DOM.
- Vitest: `plainDocument`, `extractHtmlText`, `importEpub` (фикстура-EPUB в репозитории), `translationMatchScore`, `searchDictionary` на срезе словаря, `furiganaHTML`, `dictionaryKey`, `resolveZipPath`. Цель — 70 % на `src/`.
- Playwright smoke: загрузка → демо-текст → клик по слову → поиск → смена фуриганы → перезагрузка с восстановлением позиции.
- `docs/perf.md` с базовыми числами и скриптом замера.

**Готово, когда:** `npm test` покрывает чистую логику, smoke-тест падает при регрессии, baseline зафиксирован.

### Фаза 2. Данные словаря — 8–12 дней (ядро релиза 1.1)

**Сделано в 1.2:** сборка компактного словаря на CI, «ядро» частых слов, замеры.
**Осталось:** `forms.idx`/`gloss.idx` на диске, шардирование, ленивая загрузка.

- `scripts/build-dictionary.mjs`: компактные шарды, `forms.idx`, `gloss.idx`, манифест с хэшами.
- Рантайм: загрузка по требованию, кэш шардов в IndexedDB, версионированные имена файлов (обход `max-age=600`).
- Убрать JSZip и `JSON.parse` из старта; JSZip остаётся только для импорта EPUB.
- Инкрементальная загрузка: сначала ~20–30 тыс. частотных слов (< 1,5 МБ), затем полный словарь в фоне.
- Поиск по русскому — через `gloss.idx`; убрать линейный скан.
- Ромадзи → кана в поле поиска.

**Готово, когда:** тап по слову < 50 мс, поиск по русскому p95 < 100 мс, память < 150 МБ, старт без блокировки главного потока.

### Фаза 3. Рендер и токенизация — 8–12 дней

- Виртуализация: в DOM живут абзацы в окне ±2 экрана, остальное — модель.
- Батчевая токенизация (25 абзацев на сообщение), приоритет видимой области, отменяемые задачи, инкрементальное обновление DOM по мере готовности.
- Точечный патч токена при переключении «известное» и смене режима фуриганы (без полного `renderAnalyzedText`).
- Позиция чтения по якорю `{абзац, символ}`; корректный пересчёт при смене шрифта/повороте.
- EPUB: `nav`/NCX, вложенное оглавление, обложка и иллюстрации через `Blob`-URL, метаданные, удаление `rt`/`rp`.

**Готово, когда:** книга на 300 страниц открывается с фуриганой < 3 с, автопрокрутка держит 60 fps, память не растёт от главы к главе.

### Фаза 4. Сохранность данных — 4 дня

- `navigator.storage.persist()` + индикатор статуса.
- Версионирование схемы IndexedDB и миграции; `BroadcastChannel` для нескольких вкладок.
- Экспорт/импорт всей библиотеки (книги, позиции, закладки, известные слова) одним файлом.
- Синхронная запись «последней позиции» в localStorage как страховка на закрытие вкладки.
- Обработка `QuotaExceededError` с понятным сообщением, а не молчаливым `catch`.

**Готово, когда:** экспорт → очистка данных → импорт полностью восстанавливает состояние; переполнение квоты не теряет данные незаметно.

### Фаза 5. PWA и лёгкий старт — 4–5 дней

- Service Worker (Workbox): precache оболочки, runtime-cache для vendor/data, стратегия stale-while-revalidate с версионированными URL.
- PNG-иконки 192/512 + `apple-touch-icon`, скриншоты для install-промпта.
- «Лёгкий режим»: `Intl.Segmenter` + чтения из `forms.idx`; полный Kuromoji — по кнопке.
- Экран «офлайн» и индикатор отсутствия сети.
- Пропускаемый первый запуск: «Читать сейчас, словарь позже».

**Готово, когда:** offline-перезагрузка работает; первая интерактивность на 4G < 5 с; первый запуск < 3 МБ.

### Фаза 6. Читательский UX — 8–10 дней

- Скорость в знаках/мин с пресетами, запоминание per-book.
- Тёмная и сепия-темы, выбор шрифта, «строка фокуса», режим без фуриганы для известных.
- Клавиатура: пробел/стрелки/J/K/[/], пауза в конце главы.
- ~~縦書き (вертикальное письмо)~~ — сделано досрочно в 1.1, осталось: точная привязка позиции при смене ориентации.
- TTS `ja-JP` для слова и абзаца (Web Speech API, без бэкенда).
- Мобильные жесты: свайп по области чтения — скорость/позиция; шторка словаря с подложкой и focus trap.
- Полнотекстовый поиск по книге.

**Готово, когда:** 30 минут чтения без захода в настройки; на iOS нет зума и скачков позиции.

### Фаза 7. Учебный слой — 10–15 дней

- Модель известных слов 2.0: частотность/JLPT как стартовая эвристика, покрытие текста в процентах, плотность неизвестных по главам.
- Экспорт словаря в Anki CSV и формат, совместимый с Yomitan; импорт обратно.
- Карточка кандзи: радикалы, черты, частотность, JLPT; питч-акцент из Kanjium.
- Статистика чтения: время, знаки, новые слова — локально, с экспортом.
- SRS (FSRS-lite) — только локально, без аккаунтов; включать после того, как данные перестанут теряться.

**Готово, когда:** пользователь видит прогресс и может забрать свои данные наружу.

### Фаза 8. Качество и сообщество — постоянно

- Матрица e2e: iOS Safari, Chrome Android, Firefox, Safari macOS.
- Visual regression на ключевые экраны.
- `docs/ARCHITECTURE.md`, ADR на каждое крупное решение, `CONTRIBUTING.md`.
- Диагностика: кнопка «Сообщить о проблеме», генерирующая локальный отчёт (версия, браузер, состояние загрузки) — без отправки на сервер.

## 8. Чего не делать

- **Не переписывать на React/Svelte сейчас.** Приложение императивное и почти всё в DOM-манипуляциях; выигрыш от фреймворка не покроет стоимость миграции. Сначала модули и сборка.
- **Не добавлять бэкенд, аккаунты и облачную синхронизацию.** Это ломает главное обещание продукта. Синхронизация — только файлами.
- **Не делать SRS до фазы 4.** Повторение поверх данных, которые теряются при вытеснении IndexedDB, — худший вариант.
- **Не добавлять машинный перевод и AI-функции** в ядро чтения: задержка, стоимость, приватность.
- **Не расширять список форматов** (PDF, MOBI) до стабилизации EPUB.

## 9. Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| Мобильный браузер убивает вкладку по памяти | высокая | фаза 2 (компактные данные), фаза 3 (виртуализация); измерять на реальном Android |
| Пользователи теряют библиотеку (ITP/очистка) | высокая | фаза 4: `persist()`, экспорт, предупреждение |
| Рефакторинг ломает работающий UX | средняя | фазы 0–1: тесты и smoke до крупных изменений |
| Сборка словаря усложняет CI | средняя | артефакты кэшируются в Actions, сборка идемпотентна, хэши в манифесте |
| 縦書き окажется нестабильным | средняя | отдельный режим с feature detect, не трогает основной поток |
| Один разработчик + растущая сложность | высокая | дробить на модули, писать ADR, не брать больше одной крупной темы за релиз |
